# Technical test and evaluation strategy

**Use when:** requirements need a defensible verification/validation evidence strategy or a test result must be interpreted across configuration and operating boundaries.

**Do:** trace every claim to requirement, method, level, article/configuration, environment, instrumentation, sample rationale, acceptance criteria, independence, raw data, anomaly path, and authority; distinguish developmental learning from formal acceptance; preserve failed/anomalous evidence.

**Stop when:** configuration, procedure, measurement fitness, safety readiness, deviation/retest authority, or acceptance ownership is unresolved.

**Output:** requirement-to-evidence matrix, strategy, readiness record, calculation receipts, raw/result lineage, anomalies, limitations, residual risk, and approval packet. See [the playbook](../playbooks/technical-management/07-test-and-evaluation-strategy.md).
